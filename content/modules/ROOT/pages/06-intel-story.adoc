= Module 6: The Intel Xeon Story

_Estimated time: 5 minutes_

In this module you will explore why CPU-based inference matters for tool calling workloads, check for Intel-specific optimizations, and understand when {intel_platform} processors are the right choice for agentic AI.

== Why CPU Inference Matters for Tool Calling

Tool calling workloads have a distinctive performance profile. The model generates a short structured response (the tool call JSON), waits for the tool to execute, then generates another short response. This stop-and-go pattern is fundamentally different from long-form text generation, and it plays to CPU strengths:

* *Short output sequences* -- Tool call responses are typically 50-200 tokens of JSON, not pages of text
* *I/O-bound latency* -- The bottleneck is often the external tool (API call, database query), not the model inference
* *Lower concurrency* -- Agentic workflows are typically per-user, not batch processing
* *No additional hardware cost* -- You are running inference on {intel_platform} servers you already own

== Check Intel Optimizations

The vLLM CPU runtime includes optimizations for Intel instruction set extensions. Check the node hardware:

[source,bash,role="execute",subs="attributes+"]
----
oc get nodes -o custom-columns=NAME:.metadata.name,CPU:.status.capacity.cpu,MEMORY:.status.capacity.memory
----

Depending on the {intel_platform} generation in your cluster, the runtime may leverage:

* *AVX-512* -- Advanced Vector Extensions that accelerate matrix operations. Available on 3rd Gen Intel Xeon Scalable (Ice Lake) and later.
* *AMX (Advanced Matrix Extensions)* -- Hardware acceleration for INT8 and BF16 matrix multiply. Available on 4th Gen Intel Xeon Scalable (Sapphire Rapids) and later.
* *VNNI (Vector Neural Network Instructions)* -- Optimized instructions for inference workloads.

These extensions narrow the performance gap with GPU, particularly for smaller models and the short-output patterns common in tool calling.

== The Cost Perspective

Consider deploying an agentic assistant that calls three tools per user query:

* *GPU path:* Procure GPU hardware, set up GPU operator, configure node affinity, manage drivers. Timeline: weeks to months. Cost: thousands per month.
* *CPU path:* Deploy on existing {intel_platform} infrastructure. Same OpenShift cluster as your other workloads. Timeline: the `oc apply -k` command you ran in Module 2. Additional hardware cost: zero.

For tool calling workloads where the model produces short outputs and waits for external tools between turns, CPU inference delivers the same functionality at a fraction of the cost.

== When to Use CPU for Tool Calling

[cols="1,2"]
|===
| Workload | Why CPU Works

| *Agentic assistants*
| Short outputs, tool wait times dominate latency

| *API orchestration*
| Model routes requests to the right API; output is structured JSON

| *Data retrieval agents*
| Model queries databases and summarizes results; I/O is the bottleneck

| *Small to medium models (< 14B)*
| Fit comfortably in system memory with acceptable inference speed
|===

== Verify Resource Usage

Check how much CPU and memory the model serving workload is consuming:

[source,bash,role="execute",subs="attributes+"]
----
oc adm top pods -n {project_name}
----

Note the resource usage. Tool calling models on CPU typically use moderate resources because the inference is intermittent -- the model is idle while tools execute.
